<objective>
Prove persistence: a hand-written migration that applies *and* rolls back, a throwaway per-run database so tests never touch working data, and a round-trip that shows every accepted contract payload survives a JSONB write/read unchanged.

Purpose: criterion 5 requires the migration to apply and roll back and the fixtures to round-trip unchanged. D-07 fixes the physical shape — validated JSONB document plus promoted columns — and warns that changing the document/promotion split after records exist requires a data migration. D-35 requires two database roles so tests are reproducible and never mutate development data. This plan asks for the plan's newest architectural decisions, so the downgrade path and the throwaway fixture are treated as first-class deliverables, not afterthoughts.

Output: the Alembic configuration and environment, the hand-written migration, the session-scoped throwaway-database fixture, and the two round-trip integration tests that constitute criterion 5's evidence.

Wave note: this plan moved from wave 4 to wave 5 and now depends on plan 08, because it edits `apps/api/pyproject.toml` — created by plan 08 — to add the Alembic and SQLAlchemy dependencies and to place the migration tree beside the distribution that owns it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test suite → database | tests create and drop databases on the same server that holds development data |
| application → database schema | DDL is generated from the migration, which must not be injectable |
| migration rollback → schema state | a broken downgrade leaves objects behind and blocks a clean re-apply |
| JSONB document → reader | a Decimal stored as a JSON number would round-trip through a float and lose precision |
