<objective>
Make the skeleton observable without making it leaky: structured JSON logs that are redacted before they are rendered, one correlation ID minted per request and propagated to logs, spans and responses, and local on-disk traces that need no collector.

Purpose: criterion 4 requires logs and traces that never expose a secret and that let a single request be followed end to end. The redaction processor and the correlation-ID middleware are the mechanism, and they must exist before any later phase emits a record — a phase that logs first and redacts later has already leaked. Splitting this off the original plan-01 keeps the tracer thin: plan 08 proves the chain, this plan makes it observable, and both stay inside the file budget.

Wave note: this plan moved from wave 3 to wave 4 and now depends on plan 08 *and* plan 10. Its logger and tracer read `log_level` and `trace_file_path`, and those two keys are declared by plan 10's `Settings` extension — at wave 3 this plan and plan 10 ran in parallel with no edge between them, so the prerequisite could be absent (settings.py is not among this plan's `files_modified`, so this plan cannot declare the keys itself, and the tracer would have fallen back to a literal path while plan 10's keys stayed inert). The edge is declared here rather than implied by neither plan naming the other. No downstream plan depends on this plan, so nothing else re-waves.

Output: `logging.py` (structlog configuration plus the redaction processor), `middleware.py` (per-request correlation ID), `tracing.py` (local OTel-to-disk traces), the `app.py` wiring, and the two unit test modules that prove redaction and propagation.
</objective>

    In `middleware.py`, implement a Starlette `BaseHTTPMiddleware` that mints a fresh `uuid.uuid4()` correlation ID per request, binds it with `structlog.contextvars.bind_contextvars(correlation_id=...)`, clears the contextvars in a `finally` block after the response, and sets the same ID as a response header `X-Correlation-ID`. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process → logs/traces on disk | structured records and spans are written to repo-local files that outlive the process |
| client → server | a request may carry headers (including a forged `X-Correlation-ID`) that the server must not trust |
| logging context → rendered output | any value bound into the context can reach a rendered line |
